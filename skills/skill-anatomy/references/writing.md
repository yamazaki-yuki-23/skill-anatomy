# 分析レポートの書き方

読み手は、スキルを使った経験があり、その設計の理由を知りたいエンジニア。GitHubとMarkdownの基本は前提にしてよい。設計理論、エージェントの内部実装、読み手の等級は前提にしない。個別分析と全体分析の両方に次の書き方を使う。

## 理解を助ける書き方

1. 最初に、そのスキルの役割と、作者が向き合った課題・中心となる設計判断を短く示す。概要の冒頭近くにその1文を置く（HTML版は冒頭の最初の文を先頭に使う）。調査日やファイル一覧から始めず、調査記録は末尾に置く。見出しは本文で扱う話題が分かる言葉にする。
2. 短く、普段の言葉で、敬体（です・ます）で書く。独自用語や理論名・手法名を説明の軸にせず、動作を言葉で説明する。ファイル名・スキル名・コードは原表記を保ち、同じ概念の名称を言い換え続けない。リンクは「入口」のような造語でなく、「使う条件と出力形式」のように指す内容が分かる言葉に付ける。特定のエージェント製品向けの説明は、対象の動作に必要な場合だけ書く。
3. 原文の指示を取り上げたら、具体的な場面で誰の行動がどう変わるか説明する。「推奨回答がある」で止めず、利用者が何を判断するようになるかを例で示す。変更前後の説明では、何を変えたかが分かる例を使う。
4. 専門用語や略語は初出で、その場面で何を指すか短く説明する。
5. 設計は理由を先に書き、具体的な動作と条件を続ける。要点を無理に3つへ分けない。
6. 1段落で扱う主張を絞り、主語・対象・条件を追える文にする。「設計の本質が効く」など、動作が分からない表現は具体化する。
7. 手順は番号、比較は表、因果や説明は段落を使う。図は関係を追いやすくなる場合に使い、各図表に何を読み取るかを添える。太字は重要な判断に絞り、文全体の強調や説明の全面的な箇条書きはしない。
8. 分量は `complete` が検査する範囲（個別分析 5,000〜24,000バイト、全体分析 1,500〜12,000バイト、各章の本文 40バイト以上）に収める。範囲は作例2組から決めた目安で、小さな対象は下限近くで終え、足りない分を補わない。上限を超えたら、読み手の判断に関係しない説明から削る。流れは代表例1つの経路だけを追い、別の入口や補助の経路は存在と役割を1段落にまとめる。設計は理由・動作と条件・出典を1〜2段落で書く。経緯は結論に関係する変更に絞る。細かな数値や設定値は、判断の条件になるものだけ残す。必要な理由・例・条件・出典は残す。

短さだけで選ばず、理由・条件・根拠が残るかを見る。「意味保持を優先する」で終えず、条件が消える危険を示し、「案を原文と比べ、意味が変わるなら原文を残す」と動作まで説明して出典を付ける。固定コミット、履歴・議論の確認、調査の終了条件、未確認事項の記録は、短くするために省かない。

## 推敲

保存前に個別分析と全体分析を続けて読み、次の順で直す。

1. 各段落が加える事実・理由・条件・例を確かめる。同じ対象範囲や制約の再説明、既出の説明を言い直すだけの末尾は、必要な一箇所や参照へまとめる。処理の順序と設計の理由など、役割が違う説明は残す。個別分析が範囲を超えていたら、実例が通らない経路の手順、条件にならない数値の順に削る。
2. 一読で主語・対象・動作を特定できるか確かめる。複数の意味に取れる参照語は対象名へ戻し、初出の専門用語には説明を添える。数値が条件なのか推奨なのかを原文と照合する。表のラベルを本文の語尾へ転用せず、文として述べ切る。自然な語尾を変化のためだけに直さない。
3. 修正箇所を原文と照合し、意味・出典・条件・断定の強さを保ったか確かめる。作者の発言、差分の事実、分析者の読み解きを混ぜない。実例が手順と理由を説明できることを確認し、必要な内容を短縮で失ったら戻す。
