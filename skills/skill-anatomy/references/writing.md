# 分析レポートの書き方

読み手は気に入ったスキルの仕組みと設計判断を学びたいエンジニア。次の書き方を、個別分析と全体分析の両方に使う。

## 理解を助ける書き方

1. 最初に、そのスキルの役割と学べる設計を短く示す。調査日やファイル一覧から始めず、調査記録は末尾に置く。見出しは、本文で扱う話題が分かる言葉にする。
2. 原文の指示を取り上げたら、具体的な場面で誰の行動がどう変わるか説明する。「推奨回答がある」で止めず、利用者が何を判断するようになるかを例で示す。変更前後や別用途への変更では、何を変えたかが分かる例を使う。章ごとの説明の分担は[形式と完成基準](report-format.md)に従う。
3. 専門用語や略語は初出で、その場面で何を指すか短く説明する。同じ概念の名称を言い換え続けず、コード・ファイル名は原表記を保つ。
4. 1段落で扱う主張を絞り、主語・対象・条件を追える文にする。「設計の本質が効く」など、動作が分からない表現は具体化する。
5. 手順は番号、比較は表、因果や説明は段落を使う。図は関係を追いやすくなる場合に使い、各図表に何を読み取るかを添える。太字は重要な判断に絞る。文全体を強調したり、説明をすべて箇条書きにしたりしない。

## 推敲

保存前に個別分析と全体分析を続けて読み、次の順で直す。

1. 各段落が加える事実・理由・条件・例を確かめる。同じ対象範囲や制約の再説明、既出の学びを言い直すだけの末尾は、必要な一箇所や参照へまとめる。処理の順序と設計の理由など、役割が違う説明は残す。
2. 一読で主語・対象・動作を特定できるか確かめる。複数の意味に取れる参照語は対象名へ戻し、初出の専門用語には説明を添える。数値が条件なのか推奨なのかを原文と照合する。表のラベルを本文の語尾へ転用せず、文として述べ切る。自然な語尾を変化のためだけに直さない。
3. 修正箇所を原文と照合し、意味・出典・条件・断定の強さを保ったか確かめる。作者の発言、差分の事実、分析者の読み解き、仮想例を混ぜない。具体例や別用途への応用が手順と理由を説明できることを確認し、必要な内容を短縮で失ったら戻す。

## 参考にした工夫

[i-have-adhd](https://github.com/ayghri/i-have-adhd/blob/main/skills/i-have-adhd/SKILL.md) は答えを先に出すこと、手順を番号で示すこと、成果を具体的に見せることを重視する。本スキルのレポートでは「役割と学びを先に示す」「処理を具体例で追う」という書き方へ応用した。静的な解説なので、会話用の次の行動や進捗報告は本文へ持ち込まない。

[yomiyasu](https://github.com/nanaism/yomiyasu/blob/main/skills/yomiyasu/SKILL.md) は意味と断定の強さを保ち、主述・修飾・条件の関係を確かめて推敲する。本スキルのレポートでは設計判断の理由や適用条件を短縮で失わないこと、作者の意図を補わないことへ応用した。ここに必要な書き方を記載しているため、利用環境にこれらのスキルがなくても適用できる。
