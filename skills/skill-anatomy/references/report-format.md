# レポートの形式と完成基準

執筆前に[分析レポートの書き方](writing.md)と、作成する種類のテンプレートを読む。

## 固定する形式

- 個別分析は[個別分析テンプレート](../assets/templates/skill-analysis.md)を使う。
- 全体分析は[全体分析テンプレート](../assets/templates/repository-analysis.md)を使う。

タイトルの型、`##` 見出しの名称と順序、調査記録の項目をそろえる。`###` 以下の小見出し、段落、図表、具体例、説明の分量は対象に合わせる。テンプレートの `{{...}}` は内容に置き換え、案内文や空欄を残さない。見出しは省略せず、情報がない場合は不明・未確認の範囲を書く。

形式をそろえる目的は、読み手が同じ場所で使い方・経緯・設計・応用を探せるようにすること。重要な設計の説明を短縮したり、章の分量を均等にしたりする必要はない。新しい形式は新規作成・再分析する文書に適用し、変更のない過去レポートを形式変更だけで書き換えない。

## 個別分析の完成基準

次の点を、書いた文書だけで読み手が説明できるか確かめる。

1. 使う場面、必要な入力、結果までの流れ。呼び出し先を含む役割分担。
2. 重要な指示や構成が対処する課題と、その指示が具体的な場面で変える行動。
3. 作者が述べた理由、変更前後で確認できた事実、分析者の読み解きの違い。
4. 別の課題へ応用できる条件、実際の指示・構成の例、元スキルから変える点と理由。

「推奨回答を付ける」「手順を分割する」といった観察で止まっていれば、具体例で仕組みを説明する。経緯が日付とコミット名だけなら重要な差分と理由を調べる。応用例が名前の置換だけなら別用途での判断を掘り下げる。見出しを埋めただけで完了にしない。

## 全体分析と中断時

全体分析は個別分析の要約を並べるだけで終えず、複数スキルの具体例から共通する考え方と使い分けを説明する。個別URLでは調査した範囲に限定する。

件数はPLANと状態ファイルから数える。途中もスキル一覧と未完了範囲を保存し、共通する設計は全件完了まで「未集約」とする。未完了の全体分析に `complete --repository` を実行しない。
