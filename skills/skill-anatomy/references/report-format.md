# レポートの形式と完成基準

執筆前に[分析レポートの書き方](writing.md)と、作成する種類のテンプレートを読む。この文書は章の役割と完成基準、テンプレートは見出しと記入欄、書き方は表現と保存前の推敲を扱う。

## 固定する形式

- 個別分析は[個別分析テンプレート](../assets/templates/skill-analysis.md)を使う。
- 全体分析は[全体分析テンプレート](../assets/templates/repository-analysis.md)を使う。

タイトルの型、`##` 見出しの名称と順序、調査記録の項目をそろえる。`###` 以下の小見出し、段落、図表、具体例、説明の分量は対象に合わせる。テンプレートの `{{...}}` は内容に置き換え、案内文や空欄を残さない。見出しは省略せず、該当しない章はその理由や個別分析への案内を短く書く。取得できなかった情報は調査記録にまとめ、主張の解釈が変わる箇所だけ本文にも条件を添える。

形式をそろえる目的は、読み手が同じ場所で使い方・経緯・設計・応用を探せるようにすること。重要な設計の説明を短縮したり、章の分量を均等にしたりする必要はない。新しい形式は新規作成・再分析する文書に適用し、変更のない過去レポートを形式変更だけで書き換えない。

## 章に置く内容の判断

個別分析の「仕組みと処理の流れ」は代表的な入力から出力までを具体例でたどる。「設計判断と学べること」は、その流れで重要な選択がどの課題に対処し、どの条件で役立つかを説明する。「自作スキルへの応用」は別用途の課題を選び、適用条件、指示や構成の具体例、元スキルから変える点と理由、応用する範囲の境界を示して終える。設計の一覧は設計章に置き、応用章の末尾で再列挙しない。同じ例を使う章では前の手順を再説明せず、新しく説明する判断だけを書く。重要な設計の課題・具体的な動作・根拠・適用条件が伝わったところで説明を終える。

説明の主語は調査対象のスキルにする。分析者が履歴や発言を照合した方法は、対象スキルの設計として扱わない。取得制約が結論に影響した範囲は「調査範囲と出典」へ、PLANやCLIの診断・操作経過は利用者への作業報告へ分ける。分析件数と対象範囲は全体分析に残す。

## 個別分析の完成基準

次の点を、書いた文書だけで読み手が説明できるか確かめる。

1. 使う場面、必要な入力、結果までの流れ。呼び出し先を含む役割分担。
2. 重要な指示や構成が対処する課題と、その指示が具体的な場面で変える行動。
3. 作者が述べた理由、変更前後で確認できた事実、分析者の読み解きの違い。
4. 別の課題へ応用できる条件、実際の指示・構成の例、元スキルから変える点と理由。

「推奨回答を付ける」「手順を分割する」といった観察で止まっていれば、具体例で仕組みを説明する。経緯が日付とコミット名だけなら重要な差分と理由を調べる。応用例が名前の置換だけなら別用途での判断を掘り下げる。見出しを埋めただけで完了にしない。

## 全体分析と中断時

全体分析は調査した範囲に限定する。対象が1スキルなら、概要と一覧で目的・構成・必要な環境、件数と対象範囲を示す。対象外の説明も概要の分析状況にまとめ、一覧の後へ補足しない。関係と設計の解説は個別分析へ集約し、全体の対応する章はテンプレートの参照リンクで完結させる。調査記録はファイル・履歴・議論の確認範囲と出典を記し、経緯や判断の説明を再掲しない。

対象が複数なら、成果物の受け渡し、呼び出しの有無、共通する判断と使い分けを説明する。関係の説明に必要な違いを取り上げ、各スキルの手順や具体例の詳細は個別分析へリンクする。

件数はPLANの選択範囲と、完了応答または状態ファイルの現在の状態から数える。途中もスキル一覧と未完了範囲を保存し、共通する設計は全件完了まで「未集約」とする。未完了の全体分析に `complete --repository` を実行しない。
