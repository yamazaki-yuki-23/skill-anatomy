# 分析ドキュメント

日本語で書く。コード・コマンド・ファイル名は元の表記を保つ。一般的なスキル作成の説明で埋めず、そのスキルの根拠と具体例を書く。下の構成は内容を整理する目安で、空の項目を埋めるために推測しない。

## 個別分析

冒頭にスキル名、元URL、分析コミット、調査日、調査範囲、実行検証なしを記載する。

1. **概要と使い方**。解決する課題、起動条件、必要な入力・依存環境、呼び出し例、得られる結果を説明する。対象がサポートしている呼び出し方だけを事実として記載する。推定した例は例であることを示す。
2. **処理の流れ**。主要な手順と、SKILL.md・参照資料・補助スクリプトの役割分担を説明する。
3. **作成・変更の経緯**。作成コミットと重要な変更、作者の説明を出典付きで記載する。動機が見つからなければ「確認できず」。取得できなければ「未確認」とする。
4. **設計の工夫と学べること**。「元の記述・構成 → エージェントの行動との関係 → 自分のスキルで使える条件」を結びつける。原文の短い引用や具体的なファイルへのリンクを添える。
5. **応用例と出典**。自作スキルへ応用した短い記述例を示す。例はこの分析で作成したものと明記する。読んだファイルと関連するコミット・PR・Issueを列挙し、取得できなかった範囲を記載する。

弱点評価・改善提案・ランキングは書かない。対象スキルを書き直す提案と、別用途への応用例を混同しない。文書として説明されている制約・必要条件は使い方に記載する。

## リポジトリ全体の分析

冒頭に元URL、今回の分析コミット、調査日、全体URLか個別URLか、完了件数と未完了件数を示す。

1. **概要**。リポジトリの目的、全体構成、必要な環境。
2. **スキル一覧**。名前、元のパス、短い役割、状態、個別分析への相対リンクを表にする。同名スキルはパスで区別する。変更なしのレポートは過去の調査日・コミットを保っていると説明する。
3. **スキル同士の関係**。共有資料、共通手順、連携の根拠を示す。個別URLでは関連箇所に限定した説明と明記する。
4. **共通する設計の工夫と応用**。全件分析が終わったら個別分析を横断してまとめる。全件未完了時は未集約と記載する。個別URLで全体の傾向を断定しない。
5. **調査範囲と出典**。対象としたコミット・ファイル・PR・Issue、未確認の範囲、削除されたスキルの過去レポートへのリンクを示す。

中断時も現在の件数と一覧を保存する。未完了の文書を `complete --repository` で完了扱いにしない。報告する件数はPLANと状態ファイルから数え、見積もりの件数を書かない。
