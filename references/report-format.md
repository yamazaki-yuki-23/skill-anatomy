# 分析ドキュメントの執筆と完成基準

日本語Markdownで、公開スキルの設計を学ぶための解説を書く。読み手が知りたいのは、そのスキルで何ができるかに加えて、作者が課題をどう捉え、どんな指示や構成で応えたか。原文を短く訳すだけで終えず、具体的な記述を根拠に仕組みを説明する。

## 個別分析の構成

見出しと順序は固定しない。スキル固有の学びが伝わる構成を選ぶ。問いの立て方が中心なら対話の具体例から、責務の分割が中心なら呼び出し関係から説明できる。概要・使い方・経緯・設計・応用を別々の章にする必要はない。内容がつながるなら、一つの設計判断の説明にまとめる。

次の問いに答える材料を、解説の中へ組み込む。

1. **何を解決するスキルか。** 誰がどんな場面で困り、何を渡すと何が得られるか。呼び出し例、必要な環境、利用条件を示す。呼び出し記法は対象が説明しているものを使い、独自に作った利用例はその旨を記す。
2. **どのように働くか。** 代表的な入力を置き、判断・処理・確認・結果を具体的にたどる。重要な参照資料や呼び出し先が、どこで何を担うかを説明する。ファイル一覧だけでは役割分担の説明にならない。
3. **なぜ今の形になったか。** 作者が述べた課題や理由、重要な変更前後を現在の設計へ結びつける。日付とコミット名だけで経緯を済ませない。構想の動機が不明ならその範囲を明記し、確認できた変更理由や仕組みは解説する。
4. **設計判断から何を学べるか。** 具体的な指示や構成を取り上げ、それがエージェントの選択・行動・情報の持ち方をどう変えるか説明する。選択の理由やトレードオフが出典にあれば扱う。自分の読み解きは区別し、作者の意図を補作しない。
5. **自分の設計でいつ使えるか。** 別の課題を1つ置き、学んだ考え方を短い指示や構成へ移す。適用できる前提、元のスキルと変える点、その理由を説明する。名前を変えただけの例や「適切に分割する」といった一般論で済ませない。例はこの分析で作ったものと明記する。

## 設計の説明の深さ

「推奨回答がある」「確認してから進む」「処理を分割している」は観察の出発点。その記述が具体的な場面で何を変えるのかまで説明する。

たとえば「質問に推奨回答を付ける」設計なら、推奨がない場合に利用者が考えること、推奨がある場合に判断することを、同じ問いの例で説明する。さらに、利用者が推奨を採用・修正・却下できることや、どの場面でその設計を使うかを示す。回答の負担が減ったという作者の発言があれば出典を添え、一般的な性能保証にはしない。

設計に関係する用語は初めて出す箇所でそのスキル内の意味を具体化する。「frontier」「seam」などを名前だけで済ませず、何を含み、次の行動をどう決めるのか説明する。読み手に原文を読ませ直して説明を補わせない。

説明の分量は判断の複雑さに合わせる。重要な設計判断は具体例を使って掘り下げ、細かな表記や機械的な設定に同じ分量を割かない。複数スキルの文章を共通テンプレートへ流し込んで仕上げない。

## 出典と調査記録

元URL、分析コミット、調査日、調査範囲、実行検証をしていないことを記録する。冒頭を長い調査記録で埋めず、詳細は末尾にまとめてもよい。

主張のそばに、根拠となる箇所へのリンクを付ける。指示の説明にはその行、変更理由には差分や作者の発言を示す。短い引用は読み解きに必要な箇所だけ使う。読んだファイル・履歴・関連PR/Issueと、取得できなかった範囲を末尾に整理する。すべての文書に同じ注意書きを繰り返さず、事実・作者の説明・読み解き・仮想例の違いが該当箇所で分かるようにする。

弱点評価・改善提案・ランキングは書かない。別用途への応用例は対象スキルを書き直す提案と区別する。

## 個別分析を完成とする前に

書いた文書だけで、読み手が次を説明できるか読み直す。

- 自分がこのスキルを使う場面と、入力から結果までの流れ。
- 重要な指示や構成について、それが対処する課題とエージェントの行動との関係。
- 作者が述べた理由、履歴で確認できた変化、分析者の読み解きの違い。
- 学んだ考え方を使える別の課題と、そこへ移す際の具体的な指示・条件。

説明できない箇所があれば、足りない根拠を調べるか解説を書き直す。「概要」「経緯」「応用例」という見出しがあるだけでは完了にしない。根拠を取得できない箇所は未確認と明記し、取得済みの情報から説明できる範囲を充実させる。

## リポジトリ全体の分析

全体分析も見出しは固定しない。リポジトリの目的と、作者が繰り返し採る設計の考え方が分かるように構成する。個別分析の要約を並べるだけで終えず、複数スキルの具体例を横断して、共通点と使い分けを説明する。

元URL、分析コミット、調査日、対象範囲、完了・未完了件数を明記する。スキル一覧には名前・元のパス・短い役割・状態・個別分析への相対リンクを載せ、同名はパスで区別する。関連スキルはどんな判断や成果物を受け渡すかまで説明する。必要な環境と出典、未確認の範囲も記す。

共通する設計の工夫と応用は全件分析後にまとめる。途中は未集約と記載し、現在の件数と一覧を保存する。個別URLでは説明を調査した範囲に限定する。変更なしの文書は過去の調査日・コミットを保ち、削除されたスキルの過去レポートはリンクを残す。未完了の文書を `complete --repository` で完了扱いにしない。
