# レポート品質の採点基準

採点者は生成された個別分析と全体分析の全文を読み、指示実行・根拠・理解応用・日本語・文量をそれぞれ0〜4点で採点する。全5軸が4点の場合だけ品質確認を合格とする。平均点で不足を補わず、未確認の軸には点数を付けない。

これは保守時の実モデル評価に使う基準で、[レポートの形式と完成基準](../skills/skill-anatomy/references/report-format.md)と[分析レポートの書き方](../skills/skill-anatomy/references/writing.md)を採点できる形にしたもの。製品の指示やテンプレートは変更しない。[安全性の機械判定](security-evaluation.md)と品質採点は別に記録する。

## 5軸の定義と4点の条件

各行の4点の条件はすべて満たす必要がある。右欄は合格に届かない例であり、欠点の一覧を網羅するものではない。

| 軸と確認すること | 4点の条件 | 3点以下になる例 |
| --- | --- | --- |
| 指示実行。入力・範囲・形式・完了条件に従ったか | 利用者の指定と選択範囲を守り、必要な個別分析と全体分析がそろう。所定の見出し・調査記録を満たし、該当しない章には理由や参照先がある。中断・対象外・取得不能を正しく区別し、未完了を完了としない。 | 必須の調査記録が欠ける。指定したスキルを扱わない。中断した全体分析を完了と報告する。 |
| 根拠。事実・発言・解釈を区別して確認できるか | 主要な仕組みと設計判断に、固定コミットのファイル・差分や特定の議論への出典がある。引用と説明が原典の条件や断定の強さを保つ。作者の理由、第三者の主張、分析者の読み解き、仮想例を区別し、未確認の理由を作らない。取得制約を記録し、結論に影響する箇所にも条件を添える。 | 出典はあるが、リンク先が主張を支えない。第三者の推測を作者の意図とする。現在のブランチへのリンクだけで分析時点を固定できない。 |
| 理解応用。仕組みと別用途への適用を説明できるか | 代表的な入力から出力まで、呼び出し先を含む役割分担を具体例で追える。重要な設計について課題・動作・理由・適用条件を説明する。応用章には別用途の課題、実際の指示や構成の例、元スキルから変える点と理由、適用の境界がある。全体分析は対象数に応じた関係や使い分けを示す。 | 「手順を分割する」で説明が終わる。応用例が名前の置換だけ。1スキルの全体分析で個別分析を再掲する。 |
| 日本語。意味と条件を一読で追えるか | 主語・対象・動作・条件の関係が明確で、専門用語には必要な説明がある。同じ概念には同じ語を使い、原文にない意図や強い断定を足さない。段落・番号・表を内容に応じて使い、本文だけで意味を追える。 | 指示語が複数の対象に読める。抽象語の列挙で動作が分からない。推敲で例外条件を落とす。 |
| 文量。理解に必要な説明を過不足なく配分したか | 重要な設計の課題・動作・根拠・適用条件を、具体例とともに必要な分量で説明する。章の役割を分け、重複する経緯・制約・学びの再列挙を避ける。短縮のために理由や例を落とさず、対象の複雑さに合わせて説明を終える。 | 均等な文字数にするため肝心の理由を削る。同じ手順を仕組み・設計・応用の各章で繰り返す。長短や文字数だけで合格にする。 |

全体分析だけでは、個別分析に置く具体例や応用の条件を満たしたと判断しない。両方を読む。対象が1スキルのときの参照リンクなど、所定の省略は欠落として減点しない。

## 0〜3点と未確認の扱い

| 点数・状態 | 判定 |
| --- | --- |
| 3点 | 軸の目的は伝わるが、4点の条件に一部不足がある。修正すべき箇所を特定できる。 |
| 2点 | 複数の主要な条件が欠け、読者が仕組み・根拠・判断を追うために大きな補足を要する。 |
| 1点 | 関連する記述はあるが、その軸の目的をほぼ果たしていない。 |
| 0点 | その軸に必要な記述がない、または内容が根本的に誤っている。 |
| 未確認 | 原典不足、生成未完了、未実読などで採点できない。0点と区別して理由を残し、合格にしない。 |

上の欠点例は説明用に作った例で、過去の実測結果や引用ではない。過去の評価は原文・条件を確認できる場合だけ別途参照し、この基準を作ったことで再採点済みとは扱わない。

## 実読と記録の手順

1. 生成前に対象SHA、原典のコミットと範囲、入力、モデル・設定、試行回数と停止条件を固定する。比較する場合は比較基点と変更の影響範囲も記録する。
2. 入力・指示・テンプレートと、生成した個別分析・全体分析の全文を読む。主要な仕組み・設計判断・引用を原典と照合する。見出しやキーワードの一致だけで採点しない。
3. 各軸に点数と根拠を書く。根拠にはレポートの章・該当箇所と、照合した原典を対応付ける。不足は場所・理由・必要な修正を記す。原典を取得できなければ、その影響範囲を未確認として残す。
4. 全5軸各4点、独立性、安全性と必要な機械検査をそれぞれ確認する。自己点検を独立確認とせず、独立した採点者・レビュー実行との関係と限界を記す。品質合格だけでマージ可とはしない。
5. 全試行の入力・原文・採点・失敗を保存する。修正後は[差分評価](maintenance.md#差分に応じた検証と証拠の再利用)で再確認範囲を決め、元の失敗を上書きしない。同じ入力を成功するまで再生成した結果で全体合格を主張しない。

記録には次の項目を残す。公開できない原文はGit管理外に保存し、公開側には確認結果と共有できない制約を記す。

```text
対象の完全SHA・比較基点と差分範囲：
原典リポジトリ・固定コミット・対象スキル・読んだファイルと議論：
入力・重点・生成に使った指示・モデル名/版・設定・実行日時・環境：
予定試行数と停止条件・実際の試行数・全試行の原文と操作ログの参照先：
採点者・実装/生成との独立性・採点日時：
指示実行 X/4、根拠 X/4、理解応用 X/4、日本語 X/4、文量 X/4：
各軸の根拠となる本文箇所・照合した原典・不足と修正方法：
未確認範囲・制約・安全性/機械検査の別記録・品質の合否：
修正後の完全SHA・影響範囲・再確認結果・再利用した証拠とその限界：
```

実際のモデル名や版を取得できない場合は、取得できた識別情報と未固定の項目を明記する。モデル名を推測で補わない。5軸各4点でも、確認した題材・生成条件を超える入力や人間の満足度は保証しない。
