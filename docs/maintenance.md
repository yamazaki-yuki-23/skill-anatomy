# 開発・保守の入口

```sh
bun run verify
```

公開スキルの構成、リンク、型、命名、書式、配布ファイル、バージョン、Vitestを検査する。1つでも失敗すれば終了コードは0にならない。検査ごとのログと結果は`.cache/harness/verify-*/`に保存される。GitHub Actionsも同じコマンドを使う。

利用者の実行環境はNode.js 22以上とGit。Bunは開発専用とする。開発にはBun 1.3.8以上も使い、初回は`bun install --frozen-lockfile --ignore-scripts`で依存を導入する。

テストは`tests/*.test.ts`、共有ヘルパーは`tests/runtime.ts`に置く。`bun run check`は本体・開発スクリプト・テストを同じstrict設定で型検査し、`bun run test`はVitestをBun上で実行する。配布物の動作はNode.jsを使うテストで確認する。

## 役割と受け渡し

以下の5つは役割の区分であり、Orca、特定エージェント、5人、5セッションを要求しない。1人が複数の役割を担う場合も、独立レビューの独立性を確認する。

| 役割 | 責務 | 次の担当へ渡すもの |
| --- | --- | --- |
| 調整 | Issueの目的・範囲・未決事項・完了条件と決定理由を整理し、担当・依存関係・権限を確認する。原文・実行ログ・判定根拠を確認して完了を判断する。 | 実装へ対応Issueと確定範囲・未決事項を渡す。QA・独立レビュー・出力品質へ完全な対象コミットSHAと評価範囲を渡す。統合前に証拠と権限を確認する。 |
| 実装 | 合意した範囲を変更し、必要なテスト・文書・配布物を更新する。未決仕様はIssueへ戻して確認する。 | 対応Issue、完全なコミットSHA、変更内容、検証コマンドと結果、既知の制約。 |
| QA | 指定SHAと完了条件に基づき、動作・回帰・配布環境を検証する。 | 対象SHA、環境、コマンド、結果、証拠の参照先、未検証範囲と合否。失敗には再現条件と期待値・実際値を添える。 |
| 独立レビュー | 実装者とは別の立場で、差分・要件との整合・安全性・検証の十分性を確認する。 | 対象SHA、指摘の場所・根拠・重要度・修正案と合否。修正後は影響範囲を再確認する。 |
| 出力品質 | スキルの判断手順や出力基準の変更時に、原典を固定した未使用題材で実モデル評価と生成レポートの実読を行う。 | 対象SHA、原典、生成条件、原文、評価根拠と制約。指示実行・根拠・理解応用・日本語・文量の全5軸で各4/4を確認する。平均点や機械検査だけで合格にしない。 |

1人で実装する場合は、実装者とは別の保守者によるPRレビューを標準とする。別のレビュー実行を使う場合は、実装から独立している根拠と限界を記録する。独立性を確保できなければ「未実施」とし、合格扱いにしない。実装者の自己点検は独立レビューを代替しない。

## 調整担当から直接指示する

利用者は目的と必要な権限を伝える。担当間の伝言は調整担当が行い、利用者向け返答の既定の次の行動に「別セッションへこの文を送って」を置かない。必要情報や権限が本当に不足する場合だけ利用者へ質問する。

1. 対応Issueと完了条件を整理し、依存関係に応じて担当を選ぶ。継続監督か完全移譲かを決め、受信担当が使える連絡手段と返信先を確認する。
2. 送信先のハンドルや宛先を実行時に確認する。特定のツールは必須にせず、利用できるセッション間の連絡手段を使う。端末IDなど実際の接続情報はローカルで管理する。
3. 下の指示項目を埋めて直接送信する。送信結果と受領記録を確認する。受信担当は範囲・権限・基点または対象SHAを確認し、受領または不足事項を指定の返信先へ返す。
4. 送信結果が不明、または再起動した場合は、受領記録と実行状態を確認する。確認せず再送したり、担当を重複起動したりしない。未受領・未着手を確認できた場合だけ再送する。
5. 継続監督では、調整担当が実装後の確定SHAをQA・独立レビューへ指定し、成果物と検証証拠を確認する。完全移譲では、受信担当が引き継ぐ責務と権限の受領を確認した後、旧担当は指揮を終了する。二重指揮をしない。

作業指示は、次の項目を埋めれば受信担当が利用者による伝言なしで実行・報告できる形にする。実際の宛先やローカルの成果物保存先はGitや公開Issueへ記載しない。

```text
目的・対応Issue・対象範囲：
依存関係・着手条件・完了条件：
対象コミットの完全SHA：実装前なら基点SHAと最終SHAの提出義務を記載
成果物・保存先・検証コマンド・報告先と連絡手段：
権限と禁止操作・継続監督か完全移譲か・受領確認の返信先：
```

たとえば実装担当は、受領返信後に指定の基点から許可された文書を変更し、検証結果と最終SHAを報告する。調整担当はその完全SHAをQA・独立レビューの指示に記入して直接送り、各担当は同じSHAに対する証拠を返信する。未承認のmaster統合・push・公開は実行しない。

## IssueからPRまで

1. 対応Issueを特定する。重複を確認し、目的・背景・対象範囲・未決事項・完了条件を記録する。仕様の選択肢、結論と決定理由、承認が必要な事項も残す。Issueの存在だけを仕様承認とみなさない。
2. 確定した範囲と権限内で実装する。作業ブランチをIssueに関連付け、仕様変更が必要ならIssueへ戻して決定を記録する。
3. 完全な対象SHAを固定して検証・レビューへ渡す。下記の検証手順に沿ってQA・独立レビュー・必要時の出力品質評価を行う。指摘を修正したら新しいSHAを渡し、影響範囲を再検証・再レビューする。
4. 作成権限がある場合にPRを作る。関連Issue、動作変更、対象SHA、検証・レビュー結果、制約を記載する。仕様の結論と理由はIssue、最終SHAの証拠はPRへ集約する。PR未作成時は公開可能な証拠の要約をIssueに残す。
5. 完了条件と操作権限を確認する。未決事項が解消され、必要な検査とレビューの証拠が揃ってから、権限のある操作だけを実行する。結果をIssue・PRに残し、統合待ちと完了を区別する。

### 証拠と公開範囲

検証・レビューの記録には、完全な対象SHA、比較基点や差分範囲、実行環境、コマンドと終了コード、判定根拠、指摘への対応、未検証範囲と制約を対応付ける。失敗の証拠も残す。修正前のSHAの証拠を、最終SHAの合格証拠として流用しない。

公開する結果は、CI実行やPRコメントなど第三者が確認できる参照先を優先する。公開不能な原文やログはGit管理せず、安全なローカル保存先に保全する。公開側には確認できた結果と、証拠を共有できない制約を要約する。

実モデル評価では原典・モデル・生成条件・試行回数を記録し、失敗した原文や採点を上書きしない。採点基準を緩めず、生成モデルに採点の正解を混ぜない。失敗を捨てて同じ題材を再試行せず、合格した題材の結果を全入力や人間満足度の保証へ広げない。

| Git管理・公開する共通情報 | Git管理しないローカル運用情報 |
| --- | --- |
| 責務、受け渡し条件、Issue・PR手順、検証基準、操作権限、公開可能な証拠の参照先 | 端末ID、セッションID、個人の絶対パス、一時ログ、実行中の担当への接続情報 |

公開文書ではリポジトリ相対パスや一般化した例を使う。ローカル運用情報や認証情報をIssue・PR・公開証拠へ転記しない。Orca固有の接続・復旧手順を共通手順の前提にしない。

### 操作権限

Issue作成、実装、PR作成、マージ、push、公開は別の権限として確認する。依頼で明示された権限とリポジトリの保護設定に従う。Issue作成、検査・レビューの合格だけでは、仕様承認や操作権限は増えない。過去の個別依頼の許可を今後の無条件許可として扱わない。未pushの承認済みコミットを、別件の作業で勝手に削除・統合・pushしない。

## 実装と検証の手順

1. 依頼の目的と、完了を判断できる条件を決める。関連する実装・スキル・既存テストを読む。
2. 不具合修正では、その不具合を再現するテストを追加する。実際の失敗を確認してから直す。
3. 必要な範囲を変更する。コードを変えた場合は`bun run build`で配布ファイルを更新する。
4. `bun run verify`を実行する。失敗した検査のログから原因を調べ、修正後に再検証する。文書だけの変更は`bun run check:skill`と`git diff --check`で確認する。
5. スキルの判断手順や出力基準を変えた場合は`bun run test:security`も実行し、生成レポートを読む。操作が安全か、根拠と解釈が分かれているか、自作への応用が具体的かを確認する。

今回の[Issue #2](https://github.com/yamazaki-yuki-23/skill-anatomy/issues/2)では、文書検査に加えて`bun run verify`、独立した内容レビューと文章評価を行う。製品の判断手順や出力基準は変えないため、製品レポートの再生成は行わない。Issue・PRテンプレートの追加も対象外とする。これは今回の合意範囲であり、文書変更すべてへの追加検証要件ではない。

検査の成功と、文章の品質確認は別に扱う。モデルが作る説明の正しさは、見出しやキーワードの一致だけでは判断しない。新しく見つかった失敗は、テストデータや攻撃例へ追加して次回も検証する。[評価の手順と限界](security-evaluation.md)も参照する。

## Codexによる保守レビュー

```sh
bun run harness:review
```

ログイン済みのCodex CLIが必要。Git管理下のテキストと差分から、読み取り用スナップショットを作る。削除ファイルにはHEAD時点の内容を添える。新規ファイルはステージしてから実行する。`.env`、認証設定、鍵ファイル、シンボリックリンク、画像、生成済みJavaScriptなどは渡さない。除外したパスは`snapshot.json`へ記録する。

モデルに渡すツールは、スナップショット内のファイル一覧と読み取りだけ。シェル、書き込み、Web検索、外部サービス連携は無効にする。通常の開発作業を行うエージェントとは別の、レビュー専用の実行である。

`AGENTS.md`、ルートの`package.json`、公開する`SKILL.md`、`src/cli.ts`を読んだ記録がなければ失敗する。指摘には実在するパス・行番号・修正案を求める。highまたはmediumの指摘があれば終了コードは0にならない。レビュー結果を修正へ反映し、再度`verify`とレビューを実行する。自動でコード変更やマージは行わない。

`.cache/harness/review-*/`に、入力のスナップショット、Codexのイベント、指摘、結果を保存する。入力のハッシュとコミットも記録する。モデルをそろえて比較する場合は、実行前に`SKILL_ANATOMY_REVIEW_MODEL`を設定する。未指定ならCodex CLIの既定モデルを使い、モデル名は固定しない。

レビューはすべての不具合を検出する保証ではない。除外したファイルと、取得できた証拠の範囲を確認する。Codexの設定項目はバージョンによって変わるため、CLI更新後は実際にレビューを実行して互換性を確認する。

## 定期運用

| きっかけ | 実行される処理 | 確認する結果 |
| --- | --- | --- |
| PR・masterへのpush | Linux・macOS、Node.js 22・24で`verify` | CI結果と14日間保存する検証ログ |
| 毎週月曜9時、日本時間 | 同じ検証と`bun audit` | 依存の脆弱性と既存処理の失敗 |
| 依存の新バージョン | DependabotがBunとGitHub Actionsの更新PRを作成 | 更新差分とCI結果 |
| `v*`タグのpush | タグの内容を検証し、成功後にGitHub Releaseを作成 | バージョン一致、公開結果 |

AIレビューと攻撃例の実モデル評価は、ログインとモデル利用を伴うためローカルから実行する。通常のCIではAPIキーを使わない。

## リリース

以下はマージ・push・公開の各権限を確認した担当が実行する。手順の記載だけで実行許可を得たとみなさない。

1. `bun run release:prepare 0.3.1`のように、次の安定版の番号を指定する。`package.json`とCLIの番号をそろえ、配布ファイルを生成する。
2. `bun run verify`と`bun run release:check v0.3.1`を実行する。
3. 差分をレビューし、コミットしてmasterへ反映する。
4. `git tag v0.3.1`で、そのコミットにタグを付ける。
5. `git push origin v0.3.1`でタグを送る。Releaseワークフローが検証後に公開する。

番号は実際の次バージョンへ置き換える。既存タグを付け替えない。タグとCLIの番号が違う場合、masterに含まれないコミットの場合、検証に失敗した場合は公開しない。公開済みリリースの上書きもしない。

`gh skill update`がソースの`SKILL.md`へ`metadata.github-*`を追加した場合、公開用の構成検査が失敗する。これは導入先を追跡する情報であり、開発元にはコミットしない。本文の変更と混ざっていないことを確認してから取り除く。
